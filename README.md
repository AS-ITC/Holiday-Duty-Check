# ตรวจเวรวันหยุด (เวอร์ชันออฟไลน์ + ฐานข้อมูลกลาง) — repo สำหรับ deploy

แอปนี้เป็น **ไฟล์ HTML เดียวจบ ใช้ GitHub Pages โฮสต์** ไม่ต้องมีเซิร์ฟเวอร์ของตัวเอง และยังใช้งานแบบ **ออฟไลน์ได้ 100%** เหมือนเดิมทุกประการ — แต่ตั้งแต่เพิ่ม **Firebase (Firestore)** เข้ามา ผลตรวจจะ sync ขึ้นฐานข้อมูลกลางด้วย ทำให้ทุกคนที่ใช้แอปนี้เห็นผลตรวจของกันและกันข้ามเครื่องได้ (ดูหัวข้อ "ฐานข้อมูลกลาง (Firebase)" ด้านล่างสำหรับรายละเอียดทั้งหมด):

- ผลตรวจ + รูปถ่าย เก็บอยู่ในเบราว์เซอร์ของเครื่องที่กดบันทึก (IndexedDB) เหมือนเดิม **และ** sync ขึ้น Firestore ให้เครื่องอื่นเห็นด้วย — ถ้าเน็ตหลุด/Firebase ล่ม/ถูกบล็อก แอปยังกรอก/บันทึกลงเครื่องได้ตามปกติทุกอย่าง ไม่กระทบการใช้งานหลักเลย
- รายชื่อผู้ตรวจ + พื้นที่/โซน + ประเภทปัญหา ("master data") ก็ **sync ขึ้น Firestore เช่นกัน** — แก้ได้จากหน้าตั้งค่าในแอปโดยตรง (ต้องใส่รหัสผ่านก่อน มีผลกับทุกคนทันที) ไม่ต้องให้ Dev แก้ `data.js` บน GitHub เหมือนเดิมอีกต่อไป — ไฟล์ **`data.js`** ยังอยู่ในฐานะ "ค่าเริ่มต้นสำรอง" เผื่อเครื่องไหนไม่เคยเชื่อมฐานข้อมูลกลางได้เลย (ดูหัวข้อ "ฐานข้อมูลกลาง (Firebase)" ด้านล่าง)

## วิธี deploy ครั้งแรก

1. อัปโหลดทั้ง 4 ไฟล์ (`index.html`, `data.js`, `จุดตรวจพื้นที่-ITC.pdf`, `คู่มือการใช้งาน_ตรวจเวรวันหยุด.pdf`) เข้า repo นี้ (root ของ repo หรือโฟลเดอร์ที่ตั้ง GitHub Pages ไว้ให้ตรงกัน — ต้องอยู่โฟลเดอร์เดียวกันหมด)
2. เปิด GitHub Pages / Netlify ให้ deploy จาก repo นี้ (เหมือนที่ทำอยู่แล้ว)
3. เปิดลิงก์เว็บ (เช่น `as-itc.github.io/Holiday-Duty-Check/`) จากมือถือ/คอมได้เลย ไม่ต้องตั้งค่าอะไรเพิ่ม
4. **สำคัญ (ครั้งแรกครั้งเดียว):** ไปที่ [Firebase Console](https://console.firebase.google.com/) → โปรเจกต์ `holiday-duty-check` → Firestore Database → แท็บ **Rules** → วาง Security Rules ตามหัวข้อ "ฐานข้อมูลกลาง (Firebase)" ด้านล่างแล้วกด Publish — **ถ้าไม่ทำขั้นนี้ก่อน แอปจะเชื่อมฐานข้อมูลกลางไม่ได้เลย** (ฐานข้อมูลเริ่มต้นมาแบบ "ล็อกไว้หมด" ไม่ให้ใครอ่าน/เขียนจนกว่าจะตั้ง Rules) — ไม่กระทบการใช้งานหลักถ้ายังไม่ทำ (แอปยังกรอก/บันทึกลงเครื่องได้ตามปกติ) แค่จะยังไม่เห็นข้อมูลข้ามเครื่องจนกว่าจะตั้ง Rules เสร็จ

## ไฟล์ PDF ทั้ง 2 ไฟล์ (แผนผังจุดตรวจ + คู่มือการใช้งาน)

หน้าแรกมีปุ่มลิงก์ไปเปิดไฟล์ PDF 2 ไฟล์ ทั้งคู่ใช้ relative path เหมือนกัน และ**ไม่ได้ฝังไฟล์ไว้ในตัว `index.html`** (ถ้าฝังจะทำให้ไฟล์ index.html ใหญ่ขึ้นมาก) ดังนั้น:

- **"📄 ดูแผนผังจุดตรวจ ITC (PDF)"** → `./จุดตรวจพื้นที่-ITC.pdf`
- **"📘 คู่มือการใช้งาน"** → `./คู่มือการใช้งาน_ตรวจเวรวันหยุด.pdf`

ทั้ง 2 ไฟล์ต้องวางอยู่ **โฟลเดอร์เดียวกับ `index.html`** เสมอ ทั้งบน GitHub Pages และถ้าแจกไฟล์ออฟไลน์ให้ใครก็ต้องส่งคู่กันไปทั้ง 3 ไฟล์ (ถ้าส่งแค่ `index.html` ไฟล์เดียว กดปุ่มไหนก็เปิดไม่ได้) — ถ้าจะเปลี่ยนไฟล์ไหนเป็นเวอร์ชันใหม่ ให้อัปโหลดไฟล์ใหม่ทับชื่อเดิมบน GitHub ได้เลย ไม่ต้องแก้โค้ดใน `index.html`

## วิธีอัปเดตรายชื่อผู้ตรวจ / พื้นที่-โซน / ประเภทปัญหา (สำหรับผู้ใช้ทั่วไป)

**วิธีหลัก (ไม่ต้องเป็น Dev):** เปิดแอป → กด ⚙️ ตั้งค่า (ระบบจะขอรหัสผ่านทันทีตั้งแต่กดปุ่มนี้ครั้งแรกของแต่ละรอบที่เปิดแอป — ดูหัวข้อ "คู่มือการใช้งาน (PDF) + Badge สถานะเชื่อมต่อ + รหัสผ่านหน้าตั้งค่า" ด้านล่าง) → แท็บ "ผู้ตรวจ" / "พื้นที่/โซน" / "ประเภทปัญหา" → เพิ่ม/ลบได้เลย การแก้ไขจะ sync ขึ้นฐานข้อมูลกลางทันที ทุกคนที่เปิดแอปจะเห็นรายการใหม่แบบ real-time ไม่ต้องรอ deploy

**วิธีสำรอง (สำหรับ Dev แก้ `data.js` บน GitHub):** ใช้เป็นแค่ "ค่าเริ่มต้นสำรอง" เผื่อมีเครื่องไหนไม่เคยเชื่อมฐานข้อมูลกลางได้เลย (เช่น เครื่องใหม่ที่ยังไม่เคยเปิดเน็ต) หรือใช้แก้ `orgList` (ฝ่าย/แผนก) ซึ่งยังไม่มีหน้าตั้งค่าให้แก้ในแอป (ดูหัวข้อ "บันทึกเพิ่มเติม 4 แบบ" ด้านล่าง) — กดไอคอนดินสอในหน้าเว็บ GitHub เพื่อแก้ไขได้เลย ไม่ต้องมีเครื่องมืออื่น:

```js
window.MASTER_DATA = {
  members: [
    { id: "m1", name: "ชื่อ-สกุล" }
    // เพิ่ม/ลบ/แก้ตามต้องการ — id ใส่อะไรก็ได้ขอไม่ซ้ำ — ไม่มี field แผนกแล้ว มีแค่ชื่ออย่างเดียว
  ],
  areas: [
    { id: "a1", location: "Zone1", zone: "Pilot Plant ชั้น 5", order: 0 }
    // order คือลำดับการแสดงจุดย่อยภายใน location (ZoneN) เดียวกัน
  ],
  zoneGroups: [
    { location: "Zone1", desc: "Pilot Plant" }
    // ชื่อ/คำอธิบายของแต่ละ Zone แสดงเป็นบรรทัดเล็กๆ ใต้ชื่อ ZoneN บนปุ่มหน้าพื้นที่ตรวจเท่านั้น
    // (เช่น "Zone1 (Pilot Plant)") ไม่บังคับต้องมีครบทุก Zone — Zone ไหนไม่มีใน list นี้ก็แค่ไม่มี
    // บรรทัดคำอธิบายโชว์ ไม่กระทบการทำงานอื่น
  ],
  issueTypes: [
    "น้ำไม่ปิด", "อุปกรณ์ไฟฟ้าถูกเปิดทิ้งไว้", "ลมรั่ว", "สารเคมีรั่วซึม", "สายไฟชำรุด",
    "ไม่ปิดประตู / หน้าต่าง", "พบสัตว์พาหะ", "น้ำรั่วซึม", "ประตูฉุกเฉินถูกเปิดใช้งาน",
    "เครื่องจักรถูกเปิดทิ้งไว้", "สารเคมี", "แก๊สรั่ว", "อื่นๆ"
    // ตัวเลือก "ประเภทปัญหา" ในฟอร์ม เพิ่ม/ลบ/แก้ชื่อได้ตามต้องการ — ใช้ list เดียวกันทุกพื้นที่
    // ดรอปดาวน์จะเรียงตามลำดับในไฟล์นี้เป๊ะๆ (ไม่เรียง ก-ฮ ให้เอง) — "อื่นๆ" ตั้งใจไว้ท้ายสุดเสมอ
  ]
};
```

**หมายเหตุ:** หน้าแรกของแอป **ไม่มีให้เลือกแผนกแล้ว และฐานข้อมูลผู้ตรวจก็ไม่มี field แผนกอีกต่อไป** — พิมพ์ค้นหาชื่อผู้ตรวจได้จากรายชื่อทั้งหมดใน `members` ตรงๆ เลย ส่วน `location` ของพื้นที่ (areas) เป็นคนละเรื่องกับผู้ตรวจอยู่แล้ว — หน้าจอเลือกพื้นที่/จุดตรวจจะแสดง**ทุก location ที่มีอยู่ใน `areas`** ให้ทุกคนเห็นเหมือนกันเสมอ

แก้เสร็จกด commit → รอเว็บ deploy ใหม่ (1-2 นาที) → มีผลเฉพาะเครื่องที่ **ยังไม่เคย** sync กับฐานข้อมูลกลางสำเร็จเท่านั้น (เครื่องที่เคย sync แล้วจะใช้ข้อมูลจากฐานข้อมูลกลางต่อไป ไม่กลับไปอ่าน `data.js` อีก) — อยากได้ list ปัจจุบัน (รวมของที่เพิ่มผ่านแอปแล้ว) ไปอ้างอิง มีปุ่ม "ดาวน์โหลดรายการปัจจุบัน" ให้ในหน้าตั้งค่าแต่ละแท็บ

## ฐานข้อมูลกลาง (Firebase)

ตั้งแต่เพิ่มฟีเจอร์นี้เข้ามา ทั้ง**ผลตรวจ (records)** และ**รายชื่อผู้ตรวจ/พื้นที่-โซน/ประเภทปัญหา/ฝ่าย-แผนก (master data)** จะ sync ขึ้น **Firestore** (โปรเจกต์ `holiday-duty-check`) นอกจาก IndexedDB ของเครื่องนั้น ๆ ทำให้ทุกคนที่ใช้แอปนี้เห็นข้อมูลของกันและกันได้ข้ามเครื่องแบบ real-time

**หลักการทำงาน (ไม่ต้องเข้าใจก็ใช้ได้ แต่เผื่อ Dev คนอื่นอยากรู้):**

- IndexedDB ในเครื่องยังเป็น "ความจริงของหน้าจอ" เหมือนเดิมทุกประการ ทุกฟังก์ชันแสดงผล/ออกรายงานอ่านจากตรงนี้อย่างเดียว — Firestore เป็นแค่ "ท่อ sync" คอยส่งข้อมูลไป-กลับให้อัตโนมัติเบื้องหลัง (ผลตรวจใช้ store `records`, master data ใช้ store ใหม่ `masterDataCache`)
- กรอกผลตรวจ → บันทึกลงเครื่องก่อนเสมอ (เห็นผลทันที ไม่ต้องรอเน็ต) → ค่อยยิงขึ้น Firestore แบบเงียบ ๆ ด้านหลัง — แก้รายชื่อ/พื้นที่/ประเภทปัญหาในหน้าตั้งค่าก็ทำงานแบบเดียวกันทุกประการ
- มีคนอื่นบันทึก/ลบ/แก้ที่เครื่องอื่น → แอปเครื่องนี้จะดึงมาอัปเดตให้อัตโนมัติแบบ real-time (ไม่ต้องกดรีเฟรชเอง) ทั้งผลตรวจและ master data
- **ถ้าเน็ตหลุด/Firebase ล่ม/โดเมน gstatic.com ถูกไฟร์วอลล์บริษัทบล็อก** — แอปยังใช้งานได้ตามปกติทุกฟีเจอร์แบบออฟไลน์ล้วน ๆ (กรอก/บันทึก/ดูประวัติ/ออก PDF-Excel/แก้รายชื่อในเครื่องตัวเองได้หมด) แค่ไม่ sync ข้ามเครื่องชั่วคราวเท่านั้น พอเน็ต/Firebase กลับมาจะ sync ให้เองอัตโนมัติ ไม่ต้องทำอะไรเพิ่ม
- รูปถ่ายเก็บแยกเป็นเอกสารย่อยใน Firestore (คนละเอกสารต่อรูป) เพื่อไม่ให้ชนขีดจำกัดขนาดเอกสารของ Firestore (1MB/เอกสาร) โดยไม่ต้องบีบอัดรูปแรงขึ้นกว่าเดิม ยังคมชัดเท่าที่ตั้งค่าไว้ในแอปทุกประการ — master data เก็บรวมเป็นเอกสารเดียว (`config/masterData`) เพราะขนาดเล็กกว่า 1MB มาก และแก้ไม่บ่อย
- **แนบรูปแล้วบันทึก ต้องเขียนรูปขึ้น Firestore ให้เสร็จก่อนเสมอ ก่อนเขียนเอกสารหลัก** (`cloudPushRecord()`) — เคยมีบั๊กที่สลับลำดับ (เขียนเอกสารหลักก่อน) ทำให้บางครั้งรูปที่เพิ่งแนบหายไปจากหน้าประวัติ/ตอนเปิดแก้ไขซ้ำ (ดูหัวข้อ "บั๊กที่แก้แล้ว" ด้านล่าง) — ถ้าจะแก้โค้ดจุดนี้ในอนาคต ต้องคงลำดับนี้ไว้เสมอ
- ผู้ใช้ไม่เห็นหน้า login ใด ๆ เพิ่มขึ้นมาเลย (ใช้ Anonymous Authentication เบื้องหลัง มีไว้กัน bot/สคริปต์แปลกหน้าที่ไม่ได้รันผ่านแอปนี้จริง ๆ ตาม Security Rules ด้านล่าง)

**Security Rules (ต้องวางใน Firebase Console → Firestore Database → แท็บ Rules → Publish ก่อนแอปจะเชื่อมฐานข้อมูลกลางได้ — ถ้าเคยตั้งไว้แค่ส่วน `records` มาก่อน ต้องอัปเดตเป็นเวอร์ชันนี้เพื่อให้ครอบคลุม master data ด้วย):**

```
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    match /records/{recordId} {
      allow read, write: if request.auth != null;

      match /photos/{photoId} {
        allow read, write: if request.auth != null;
      }
    }

    match /config/masterData {
      allow read, write: if request.auth != null;
    }
  }
}
```

กฎนี้แปลว่า "ต้อง sign-in ก่อนถึงจะอ่าน/เขียนได้" (แอปทำ sign-in แบบไม่ระบุตัวตนให้อัตโนมัติอยู่แล้ว ผู้ใช้ไม่ต้องทำอะไร) ส่วนใครก็ตามที่ไม่ได้เปิดผ่านแอปนี้จะเข้าไม่ได้เลย — ไม่ได้ล็อกเฉพาะคนใดคนหนึ่ง แค่กันคนแปลกหน้า/บอทที่ไม่ผ่านแอป

**อาการที่เจอถ้า Rules ในคอนโซลยังเป็นเวอร์ชันเก่า (ไม่มีส่วน `config/masterData`) หรือยังไม่เคย publish เลย:** เพิ่มชื่อ/พื้นที่ในหน้าตั้งค่าแล้วดูเหมือนสำเร็จ (ขึ้นในรายการทันที) แต่ sync ขึ้นฐานข้อมูลกลางไม่ได้จริง พอปิด-เปิดแอปใหม่ (หรือเปิดเครื่องอื่น) ชื่อ/พื้นที่ที่เพิ่งเพิ่มจะหายไป — **ตั้งแต่รอบอัปเดตนี้ ถ้าเกิดเหตุการณ์นี้แอปจะขึ้น toast แจ้งเตือนสีแดงทันที** ("ซิงค์ขึ้นฐานข้อมูลกลางไม่สำเร็จ..." หรือ "เชื่อมฟัง Firestore สำหรับรายชื่อ/พื้นที่ไม่สำเร็จ...") ไม่เงียบเหมือนเดิมอีกต่อไป ถ้าเห็น toast แบบนี้ ให้ไปเช็ค/อัปเดต Security Rules ตามด้านบนก่อนเป็นอันดับแรก

**บั๊กที่แก้แล้ว #2 — แนบรูปแล้วบันทึก พอไปดูหน้าประวัติ/เปิดแก้ไขซ้ำ รูปหายไปเฉยๆ ต้องถ่ายใหม่ถึงจะติด:** สาเหตุคือ `cloudPushRecord()` เดิมเขียนเอกสารหลักของผลตรวจ (`records/{id}`, มี `photoCount` ตั้งไว้แล้ว) ขึ้น Firestore **ก่อน** ที่รูปจะเขียนเข้า subcollection `photos` เสร็จ — `startCloudSync()` ฟัง real-time เฉพาะเอกสารหลักเท่านั้น พอเอกสารหลักเขียนเสร็จปุ๊บ ระบบ sync (รวมถึงเครื่องเดียวกันเองที่รับ echo กลับมา) จะรีบไปอ่านรูปจาก subcollection ทันที ถ้าไปจังหวะที่รูปยังเขียนไม่เสร็จ จะได้ `photos: []` ว่างเปล่ากลับมา แล้วเอาไปทับข้อมูลที่ถูกต้องใน IndexedDB ของเครื่องนั้นเอง (เกิดขึ้นได้ไม่แน่นอนตามจังหวะเน็ต ตรงกับอาการที่เจอ) **แก้แล้ว**โดยสลับลำดับ: เขียนรูปเข้า subcollection ให้เสร็จ (รวมถึงลบรูปเก่าที่เกินออกถ้าแก้ไขแล้วรูปน้อยลง) ก่อนเสมอ แล้วค่อยเขียนเอกสารหลักทีหลัง ตรวจสอบแล้วด้วยเทสต์อัตโนมัติที่จำลองบั๊กนี้ได้จริง (รันกับโค้ดเวอร์ชันก่อนแก้แล้วเทสต์ fail ตรงตามอาการ รันกับเวอร์ชันแก้แล้วผ่านหมด)

**บั๊กจริงที่เจอ (แก้แล้วในรอบอัปเดตนี้ — ไม่เกี่ยวกับ Rules เวอร์ชันเก่า/ใหม่เลย):** ต่อให้ Rules เป๊ะตามด้านบนทุกตัวอักษรก็ตาม โค้ดเวอร์ชันก่อนหน้านี้ยังมีบั๊กที่ทำให้ sync รายชื่อ/พื้นที่ "ไม่เคยทำงานได้จริงเลยสักครั้ง" ข้ามเครื่อง — สาเหตุคือ rule `match /config/masterData { ... }` เป็น rule ที่ผูกกับ **เอกสารเดี่ยวตายตัว** (ไม่ใช่ wildcard แบบ `/records/{recordId}`) ซึ่ง Firestore จะอนุญาตแค่การอ่าน/เขียน "เอกสารนั้นตรง ๆ" เท่านั้น แต่จะ**ปฏิเสธ list query ทั้ง collection เสมอ** (เช่น `onSnapshot(collection(db,'config'))` ที่โค้ดเวอร์ชันก่อนหน้าใช้ฟังการเปลี่ยนแปลงแบบ real-time) —ผลคือ `setDoc` ตอนกดเพิ่มชื่อ "สำเร็จจริง" ขึ้น Firestore ทุกครั้ง แต่ตัว listener ที่ควรจะรับข้อมูลกลับมาโชว์ (หรือรับการแก้จากเครื่องอื่น) กลับ error แบบเงียบ ๆ ตลอด (ไม่มี toast เตือนในเวอร์ชันก่อนอัปเดตนี้) ทำให้ไม่มีเครื่องไหนเห็นการ sync ข้ามเครื่องได้เลยตั้งแต่แรก **แก้แล้ว** โดยเปลี่ยนไปฟัง/อ่าน "เอกสารเดี่ยว" (`onSnapshot(doc(db,'config','masterData'))` / `getDoc(doc(...))`) ตรง ๆ แทนการฟังทั้ง collection ตรวจสอบแล้วว่า sync ข้ามเครื่องทำงานถูกต้องด้วยเทสต์อัตโนมัติที่จำลองพฤติกรรม Rules แบบนี้ของ Firestore จริง

**หมายเหตุเรื่องความปลอดภัยของ "รหัสผ่านแก้ไขรายชื่อ" (`admin123`):** รหัสผ่านนี้เป็นการล็อกฝั่ง UI เท่านั้น (เหมือนโหมดทดสอบ) ไม่ใช่ระบบสิทธิ์ระดับ enterprise จริงจัง (แบบนั้นต้องมี Cloud Functions + custom claims ซึ่งต้องใช้แผนเสียเงิน Blaze) — ใครก็ตามที่เปิดแอปนี้ได้ (สิทธิ์ `auth != null` เดียวกับ records) เขียนตรงผ่าน Firestore API ได้ถ้ารู้วิธี ข้ามหน้าตั้งค่าไปเลยก็ได้ในทางเทคนิค แต่ก็เป็นความเสี่ยงระดับเดียวกับ records ที่มีอยู่แล้ว เหมาะกับเครื่องมือใช้ภายในองค์กรแบบนี้ ถ้าต้องการความปลอดภัยเข้มกว่านี้ต้องคุยเรื่องงบประมาณ/สถาปัตยกรรมเพิ่มเติม

**ปุ่ม "ล้างแคชผลตรวจในเครื่องนี้" (หน้าตั้งค่า → ข้อมูล) เปลี่ยนความหมายไปแล้ว:** เดิมทีปุ่มนี้ลบข้อมูลทิ้งถาวรเพราะข้อมูลอยู่แค่ในเครื่อง แต่ตอนนี้มีฐานข้อมูลกลางคอยเก็บสำเนาไว้ด้วย กดปุ่มนี้จึงแค่ **ล้างแคชผลตรวจในเครื่องนั้นชั่วคราว** (ไม่กระทบ master data cache) — ถ้าเครื่องนั้นยังเชื่อมฐานข้อมูลกลางได้ปกติ ข้อมูลจะถูกดึงกลับมาใหม่อัตโนมัติทันทีที่เปิด/รีโหลดแอปครั้งถัดไป ถ้าต้องการลบทิ้งจริงทั้งองค์กร ตอนนี้มีปุ่ม **"ลบข้อมูลในฐานข้อมูลกลางทั้งหมด"** ให้กดในแอปได้เลยแล้ว (ดูหัวข้อ "ส่งออก/ลบฐานข้อมูลทั้งหมด (หน้าตั้งค่า → ข้อมูล)" ด้านล่าง) ไม่ต้องเข้า Firebase Console เองอีกต่อไป

**ย้าย/ตั้งต้นข้อมูลเก่าขึ้นฐานข้อมูลกลางครั้งแรก:**
- ผลตรวจที่มีอยู่ในเครื่องต่าง ๆ ก่อนเปิดใช้ Firebase จะถูกย้ายขึ้น Firestore ให้อัตโนมัติครั้งเดียวตอนเปิดแอปครั้งแรกหลังอัปเดต (ถ้าเครื่องนั้นเชื่อมเน็ต/Firebase ได้ตอนนั้น) กันข้อมูลเก่าไม่ให้ตกหล่นไปจากสายตาเครื่องอื่น
- Master data (รายชื่อ/พื้นที่/ประเภทปัญหาจาก `data.js`) จะถูกตั้งต้นขึ้นฐานข้อมูลกลางให้อัตโนมัติ **ครั้งเดียวเท่านั้น** ตอนที่ฐานข้อมูลกลางยังไม่เคยมีข้อมูลชุดนี้เลย (เช็คจากฐานข้อมูลจริง ไม่ใช่ localStorage ของเครื่องไหนเครื่องหนึ่ง) — หลังจากนั้นการแก้ไขทุกครั้งต้องทำผ่านหน้าตั้งค่าในแอปเท่านั้น แก้ `data.js` บน GitHub จะไม่มีผลกับเครื่องที่เคย sync แล้วอีกต่อไป

## คู่มือการใช้งาน (PDF) + Badge สถานะเชื่อมต่อ + รหัสผ่านหน้าตั้งค่า

หน้าแรกของแอปมี 3 อย่างเพิ่มมาให้ผู้ใช้ทั่วไปเห็นสถานะและเข้าถึงคู่มือได้เองโดยไม่ต้องพึ่ง Dev:

- **ปุ่ม "📘 คู่มือการใช้งาน"** (ใต้ปุ่ม "เริ่มตรวจเช็คตามลำดับ" คู่กับปุ่ม "📄 ดูแผนผังจุดตรวจ ITC (PDF)") — เปิดไฟล์ `คู่มือการใช้งาน_ตรวจเวรวันหยุด.pdf` ในแท็บใหม่ทันที (ไม่มี modal ในแอปอีกต่อไป — เคยมีปุ่ม ❓ เปิดสรุปวิธีใช้งานในแอป ถูกเอาออกแล้ว เพราะดูแลเนื้อหา 2 ที่ให้ตรงกันยาก ใช้ไฟล์ PDF ฉบับเดียวแทน) ไฟล์นี้ใช้ path แบบ relative เหมือนไฟล์แผนผังจุดตรวจ ITC ทุกประการ — **ต้องวางไว้โฟลเดอร์เดียวกับ `index.html` เสมอ** ทั้งบน GitHub Pages และถ้าแจกไฟล์ออฟไลน์ก็ต้องส่งคู่กันไปทั้ง 3 ไฟล์ (`index.html`, `จุดตรวจพื้นที่-ITC.pdf`, `คู่มือการใช้งาน_ตรวจเวรวันหยุด.pdf`)
- **Badge เชื่อมต่อ (ไอคอนถัดจากชื่อแอป)** — แสดงสถานะการเชื่อมฐานข้อมูลกลางแบบเรียลไทม์ ไม่ใช่ข้อความตายตัว:
  - **☁️ เชื่อมฐานข้อมูลกลาง** (เขียว) = เชื่อม Firestore สำเร็จ ข้อมูลกำลัง sync ข้ามเครื่องตามปกติ
  - **💾 ออฟไลน์** (เทา) = ยังเชื่อมฐานข้อมูลกลางไม่ได้ตอนนี้ (เน็ตหลุด/ถูกบล็อก/ยังไม่ตั้ง Security Rules) แต่แอปยังใช้งานได้ครบทุกฟีเจอร์ตามปกติ แค่ยังไม่ sync ข้ามเครื่องชั่วคราว พอเชื่อมได้จะเปลี่ยนเป็น ☁️ ให้เองอัตโนมัติ ไม่ต้องกดอะไรเพิ่ม
- **ปุ่ม ⚙️ ตั้งค่า ต้องใส่รหัสผ่านทันทีที่กด** — เปลี่ยนจากเดิม (เดิมกดเข้าไปดูรายการได้ฟรี แล้วค่อยถูกถามรหัสตอนกดเพิ่ม/ลบจริง) เป็น **ถามรหัสผ่านทันทีตั้งแต่กดปุ่ม ⚙️ ครั้งแรกของแต่ละรอบที่เปิดแอป** ถ้าใส่รหัสผิดหรือกด Cancel จะไม่เปิดหน้าตั้งค่าให้เลย (ยังอยู่หน้าเดิม) ใส่ถูกครั้งเดียวแล้วเข้า-ออกหน้าตั้งค่า/แก้ไขได้เรื่อยๆ โดยไม่ถูกถามซ้ำจนกว่าจะปิด/รีโหลดหน้าเว็บ — logic เดิมอยู่ที่ฟังก์ชัน `confirmMasterDataEdit()` เหมือนเดิมทุกประการ แค่ย้ายจุดเรียกจากใน `addMember/addArea/addIssueType` มาเรียกที่ event listener ของ `#btnSettings` ก่อน `showModal('modalSettings')` แทน

**Dev หมายเหตุ:** logic ของ badge อยู่ที่ฟังก์ชัน `setConnStatusBadge(connected)` เรียกจาก `initFirebaseSdk()`/`initCloudAuth()` ตอนเชื่อมต่อสำเร็จ/ไม่สำเร็จตอน INIT — ถ้าจะเพิ่มข้อความ ระวัง breakpoint `@media (max-width:480px)` ที่ซ่อน `.chip-label` บนจอมือถือแคบ ควรทดสอบที่ความกว้างจอ 375-420px ด้วย

## ผลตรวจ (records)

ผลตรวจที่พนักงานกรอกจะอยู่ในเครื่องของคนกรอก (IndexedDB) **และ** sync ขึ้นฐานข้อมูลกลาง (Firestore) ให้ทุกเครื่องเห็นร่วมกันด้วย (ดูหัวข้อ "ฐานข้อมูลกลาง (Firebase)" ด้านบน) — นอกจากนี้แต่ละคนยังกด "ออกรายงาน PDF" หรือ "ส่งออก Excel" ในแท็บประวัติแยกทีละไฟล์ได้เหมือนเดิม (Excel มีคอลัมน์รูปภาพแนบฝังอยู่ในไฟล์ให้เลย เปิดดูได้ใน Excel/Google Sheets/LibreOffice) หรือกด "📧 ส่ง PDF + Excel ทางอีเมล" ทีเดียวเพื่อสร้างทั้ง 2 ไฟล์พร้อมกันแล้วส่งอีเมล — บนมือถือที่รองรับ Web Share จะเปิดหน้าต่างแชร์พร้อมไฟล์แนบทั้ง 2 ไฟล์ให้เลือกแอปอีเมลได้ทันที ส่วนบนคอมพิวเตอร์ (ที่เบราว์เซอร์ไม่รองรับการแนบไฟล์อัตโนมัติ) จะดาวน์โหลดทั้ง 2 ไฟล์ให้ แล้วเปิดดราฟต์อีเมลเตือนให้แนบไฟล์เอง

**เงื่อนไขการกดปุ่ม "ส่ง PDF + Excel ทางอีเมล":** ต้องตรวจครบทุกโซน (Zone1-Zone13 ทุกจุดตรวจย่อยในแต่ละโซน) ของวันที่กำลังตรวจอยู่ (`state.date`) ก่อน ถึงจะกดปุ่มนี้สำเร็จ — ใช้เกณฑ์เดียวกับสีการ์ดโซนในหน้า "พื้นที่ตรวจ" ทุกประการ (โซนไหนยังไม่ขึ้นสีเขียว "✅ ตรวจแล้ว" ถือว่ายังไม่ครบ) ถ้ายังตรวจไม่ครบ ระบบจะแจ้งเตือนด้วยข้อความสีแดงบอกชื่อโซนที่ยังเหลือ แล้วหยุดไม่สร้างไฟล์ใดๆ เลย (ฟังก์ชัน `allZonesCompleted()` ใน `index.html`) — เงื่อนไขนี้มีผลกับปุ่มส่งอีเมลเท่านั้น ปุ่ม "ส่งออก Excel" และ "ออกรายงาน PDF" ยังกดได้ตามปกติแม้ตรวจไม่ครบ (เผื่อกรณีต้องการเช็คข้อมูลระหว่างเวร)

**โหมดทดสอบ (ข้ามเงื่อนไขข้างบนชั่วคราว):** ในหน้าตั้งค่า → แท็บ "ข้อมูล" มีสวิตช์ "โหมดทดสอบ: ข้ามเช็คตรวจครบทุกโซน" — เปิดไว้จะกดปุ่มส่งอีเมลได้ทันทีแม้ตรวจยังไม่ครบ (ไว้ใช้ตอนทดสอบโปรแกรมเท่านั้น) เปิดสวิตช์ต้องใส่รหัสผ่าน **`admin123`** ก่อน (ตั้งไว้ในโค้ดตัวแปร `TEST_MODE_PASSWORD`) ส่วนปิดกลับคืนทำได้ทันทีไม่ต้องใส่รหัส สถานะเก็บไว้ใน localStorage ของเครื่องนั้นๆ (คนละเครื่องไม่กระทบกัน) และมีแถบเตือนสีเหลืองขึ้นใต้ปุ่มส่งอีเมลตลอดเวลาที่เปิดโหมดนี้อยู่ กันลืมปิดแล้วส่งรายงานที่ตรวจไม่ครบออกไปจริง

### ตัวกรองในแท็บ "ประวัติ"

แท็บประวัติมีตัวกรอง 4 อย่าง: **ช่วงวันที่ / ผู้ตรวจ / พื้นที่ / สถานะ**

- **ช่วงวันที่** default เป็น "วันนี้ถึงวันนี้" เสมอตอนเปิดแท็บครั้งแรก (ถ้ายังไม่เคยตั้งอะไรไว้) แก้เองแล้วกด "🔍 กรองข้อมูล" เพื่อดูช่วงอื่น
- **ผู้ตรวจ** ครั้งแรกที่เปิดแท็บประวัติในแต่ละรอบที่เปิดแอป จะดึงชื่อที่เลือกไว้ที่หน้าแรก (ช่องกรอกชื่อตอนเริ่มตรวจ) มาใส่ให้อัตโนมัติเลย ไม่ต้องเลือกซ้ำ — ถ้าเปลี่ยนตัวกรองเองหลังจากนั้น แอปจะเคารพตัวที่เลือกเอง ไม่ทับคืนให้จนกว่าจะปิด/รีโหลดหน้าเว็บใหม่ (ใช้ได้กับบันทึกทุกประเภท ไม่ใช่แค่ผลตรวจพื้นที่ — เบิกของสโตร์/ขนย้ายเครื่องจักร/อุบัติเหตุ/ผู้รับเหมาก็กรองด้วยชื่อผู้บันทึกได้เหมือนกัน)
- ตัวกรอง "ผู้ตรวจ"/"พื้นที่"/"สถานะ" กรองทันทีที่เปลี่ยนค่า (ไม่ต้องกดปุ่ม) ส่วนช่วงวันที่ต้องกดปุ่ม "🔍 กรองข้อมูล" ตามเดิม

### ส่งออก/ลบฐานข้อมูลทั้งหมด (หน้าตั้งค่า → ข้อมูล)

นอกจากปุ่ม "ส่งออก Excel" ในแท็บประวัติ (ซึ่งส่งออกเฉพาะรายการที่ตรงกับตัวกรองที่ตั้งไว้ตอนนั้น) หน้าตั้งค่า → แท็บ "ข้อมูล" มี 2 ปุ่มเพิ่มเติมสำหรับงานดูแลฐานข้อมูลระดับองค์กร:

- **"⬇ ส่งออกฐานข้อมูลทั้งหมด"** — ส่งออกผลตรวจ**ทุกรายการ**ที่มีในฐานข้อมูล (ทุกวันที่ ทุกคน ทุกพื้นที่ ทุกประเภทบันทึก รวมทั้ง 4 บันทึกเสริม) เป็นไฟล์ .xlsx ไฟล์เดียว ไม่ผ่านตัวกรองในแท็บประวัติเลย รูปแบบคอลัมน์เหมือนปุ่ม "ส่งออก Excel" ทุกประการ (มีรูปแนบฝังในไฟล์ให้ด้วย) — ไม่ต้องใส่รหัสผ่าน (แค่ export ไฟล์ ไม่กระทบข้อมูล) แต่ต้องปลดล็อกหน้าตั้งค่าด้วยรหัส `admin123` ก่อนเหมือนปุ่มอื่นๆ ในหน้านี้
- **"🗑⚠️ ลบข้อมูลในฐานข้อมูลกลางทั้งหมด"** — ลบผลตรวจ**ทุกรายการของทุกคนทุกเครื่อง**ออกจากฐานข้อมูลกลาง (Firestore) แบบถาวร กู้คืนไม่ได้ — **ต่างจากปุ่ม "ล้างแคชผลตรวจในเครื่องนี้"** ที่ล้างแค่เครื่องเดียวและข้อมูลยังดึงกลับมาได้จากฐานข้อมูลกลาง ปุ่มนี้ลบของจริงในฐานข้อมูลกลางเลย (ไม่กระทบรายชื่อ/พื้นที่/ประเภทปัญหา) เพื่อความปลอดภัยจึง **ถามรหัสผ่าน `admin123` ซ้ำอีกครั้ง** (แยกต่างหากจากรหัสปลดล็อกหน้าตั้งค่า) บวก popup ยืนยันอีกชั้นก่อนลบจริง และใช้ได้เฉพาะตอนเครื่องนั้นเชื่อมฐานข้อมูลกลางอยู่ (badge ☁️) เท่านั้น — เหมาะกับใช้ล้างข้อมูลทดสอบ/เริ่มต้นฐานข้อมูลใหม่เป็นครั้งคราว ไม่ใช่ปุ่มที่ควรกดบ่อยๆ

## บันทึกเพิ่มเติม 4 แบบ (ฟีเจอร์เสริม)

นอกจากปุ่มพื้นที่ตรวจ Zone1-Zone13 แล้ว หน้า "พื้นที่ตรวจ" จะมีการ์ดพิเศษ 4 อันเพิ่มมาให้เสมอ:

- **📦 เบิกของสโตร์** — จดบันทึกตอนมีการเบิกของระหว่างเวร
- **🚚 ขนย้ายเครื่องจักร/อะไหล่** — จดบันทึกตอนมีการขนย้ายเครื่องจักรหรืออะไหล่ระหว่างเวร
- **🚑 รายงานการเกิดอุบัติเหตุ** — บันทึกสถานที่เกิดเหตุ/ผู้ประสบเหตุ/หน่วยงาน/รายละเอียดเหตุการณ์/ผู้รับทราบ (หัวหน้างาน-จป.-ผู้บริหาร) และเลือกผลกระทบ (ไม่มีผู้บาดเจ็บ / บาดเจ็บเล็กน้อย / บาดเจ็บต้องพบแพทย์ / อื่นๆ ระบุเอง)
- **👷 ผู้รับเหมาขอเข้าพื้นที่ (นอกแผน)** — บันทึกบริษัท/ผู้ประสานงาน/จำนวนผู้เข้าปฏิบัติงาน/พื้นที่ปฏิบัติงาน/วัตถุประสงค์การเข้าพื้นที่

ทั้ง 4 อย่างเป็น **ฟีเจอร์เสริม ไม่บังคับ** — จะมี 0 รายการ หรือกี่รายการก็ได้ในแต่ละเวร ไม่ใช่ checklist ตายตัวแบบโซนตรวจ (การ์ดจะโชว์แค่จำนวนรายการทั้งหมดที่เคยกรอกไว้ ไม่ใช่สถานะรอตรวจ/ตรวจแล้ว) กดที่การ์ดจะเห็นรายการที่เคยบันทึกไว้ทั้งหมด (ทุกวันที่ ไม่ใช่แค่วันนี้) พร้อมปุ่ม ✏️ แก้ไข และ 🗑 ลบ ต่อรายการ — กดปุ่ม "+ เพิ่มรายการ" เพื่อกรอกรายการใหม่ได้เรื่อยๆ ตามที่พบจริงหน้างาน แนบรูปได้เหมือนฟอร์มตรวจพื้นที่ (บีบอัดรูปอัตโนมัติก่อนบันทึกเหมือนกัน)

บันทึกทั้ง 4 แบบนี้จะไปโผล่ในแท็บ **ประวัติ** ปนกับผลตรวจพื้นที่ (ดูคอลัมน์ "ประเภท" เพื่อแยก) และออก **Excel/PDF** ได้เหมือนกันทุกประการ (คอลัมน์พื้นที่/โซน/ประเภทปัญหา/รายละเอียด/ผู้ปฏิบัติงาน จะโชว์ข้อมูลที่ใกล้เคียงที่สุดของบันทึกประเภทนั้นแทน เช่น เบิกของสโตร์/ขนย้ายเครื่องจักร → พื้นที่ = ฝ่าย, โซน = แผนก; รายงานอุบัติเหตุ → พื้นที่ = สถานที่เกิดเหตุ, โซน = หน่วยงาน, ประเภทปัญหา = ผลกระทบ; ผู้รับเหมาเข้าพื้นที่ → พื้นที่ = พื้นที่ปฏิบัติงาน, โซน = บริษัท)

**ฝ่าย/แผนก ในฟอร์ม "เบิกของสโตร์"/"ขนย้ายเครื่องจักร" มาจากไหน?** มาจาก `window.MASTER_DATA.orgList` ใน `data.js` — เป็นรายชื่อฝ่าย/แผนกทั้งบริษัท ใช้เฉพาะ 2 ฟอร์มนี้เท่านั้น (ฟอร์มรายงานอุบัติเหตุ/ผู้รับเหมาเข้าพื้นที่ไม่มีดรอปดาวน์ฝ่าย/แผนก เพราะเป็นฟิลด์อิสระตามแบบฟอร์มกระดาษเดิม)

**Dev แก้ `orgList` ยังไงถ้ารายชื่อฝ่าย/แผนกเปลี่ยน?** แก้ไฟล์ `data.js` บน GitHub เหมือนส่วนอื่น เพิ่ม/ลบ/แก้ไอเทมใน array `window.MASTER_DATA.orgList` แต่ละไอเทมมีแค่ 2 ฟิลด์:

```js
orgList: [
  { faction: "ชื่อฝ่าย", dept: "ชื่อแผนกในฝ่ายนั้น" },
  { faction: "ชื่อฝ่าย", dept: "ชื่อแผนกอีกอันในฝ่ายเดียวกัน" },
  // ฝ่ายเดียวกันใส่ได้หลายแถว (แผนกต่างกัน) — dropdown "แผนก" ในฟอร์มจะกรองจาก faction
  // ที่เลือกไว้อัตโนมัติ ลำดับที่โชว์ในทั้ง 2 dropdown จะเรียงตามลำดับที่ปรากฏในไฟล์นี้เป๊ะๆ
  // (ไม่ได้เรียง ก-ฮ ให้เอง) เพิ่ม/ลบ/สลับตำแหน่งได้ตามต้องการ
]
```

แก้เสร็จ commit เหมือนเดิม รอเว็บ deploy ใหม่ (1-2 นาที) แล้วทุกคนจะเห็น dropdown ฝ่าย/แผนกชุดใหม่ในฟอร์มทั้งสองทันที
